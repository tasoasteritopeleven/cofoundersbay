GLOBAL MISSION
If the project is already enriched with enough technical details, do not wait. Your goal is to evolve the platform toward a state-of-the-art product, based on everything already discussed and already present in the repository, without omissions, and with the least possible future backtracking, breakage, incompatibilities, inconsistencies, technical debt, or architectural regret.

1. Do not make random changes.
2. First understand the current repository deeply.

8. Every new feature must come with corresponding UI/UX refinement, not only backend logic.

10. Treat the project as a serious startup-grade product, not a demo.

WORKING METHOD
Follow this exact order:

STEP 1 — FULL CONTEXT INGESTION
Read the repository carefully.
Inspect:
- package.json / lockfiles
- tsconfig
- env examples
- app structure
- API routes / services
- lib / utils / hooks
- components
- styles / theme files
- schema / migrations
- auth-related files
- analytics / monitoring files
- README / docs / comments
- any TODOs, dead code, duplicate patterns, legacy remnants

Do not assume. Infer only from actual code.

STEP 2 — ARCHITECTURAL DIAGNOSIS
After reading the codebase, answer internally:
- Is the current architecture coherent?
- Is it modular enough for scale-up?
- Is the current routing approach future-safe?
- Is state handling clean or fragmented?
- Is auth extensible?
- Is data access centralized or messy?
- Is the UI system reusable and consistent?
- Are there hidden bottlenecks that will cause future rework?

STEP 3 — CHOOSE THE BEST EVOLUTIONARY ARCHITECTURE
Do not force an unnecessary rewrite.
Use the best evolutionary path.

Preferred direction, unless the repository strongly dictates otherwise:
- modern TypeScript-first architecture
- clear separation between UI, domain logic, data access, and platform integrations
- component-driven frontend
- predictable design system and reusable UI primitives
- modular feature folders where appropriate
- centralized validation, typed contracts, and safe server boundaries
- database and auth patterns that can support future B2B/B2G needs
- minimal infrastructure lock-in where possible

If the project already uses:
- Next.js, prefer App Router-compatible and scalable patterns rather than legacy fragmentation
- PostgreSQL / Supabase / Prisma, keep and cleanly structure them rather than introducing chaos
- React, standardize server/client boundaries and component responsibilities

But: never migrate just for fashion. Only migrate if the long-term gain clearly exceeds the short-term risk.

Implement in this logic order unless repository reality strongly requires otherwise:

PHASE 1: FOUNDATIONAL STABILIZATION
Goal:
Create a safe, scalable baseline before feature expansion.

Tasks:
- normalize project structure
- remove obvious dead code and unsafe duplication
- standardize naming and file organization
