# UI/UX backend coverage review — read-only feasibility audit

Scope: repository inspection only. No services were started, requests sent, credentials or environment values read, tests run, records written, migrations applied, or architecture changed. This is a coverage plan, **not** evidence that a real-backend flow passed. The prior UI/UX review explicitly leaves dedicated-backend create/edit/delete, error/retry and persistence verification outstanding (`docs/UIUX_AUDIT_REVIEW.md:74-88`).

## Feasibility and isolation boundary

**Feasible conditionally, not on the current evidence alone.** The existing Next.js client and NestJS/Prisma API can be pointed at an *independently provisioned, disposable* PostgreSQL database and optional isolated Redis/Meilisearch services without replacing their architecture (`apps/api/prisma/schema.prisma:5-10`, `apps/api/src/app.module.ts:76-125`, `docker-compose.yml`). Use newly issued test-only accounts for each role and tenant, test-only email/provider configurations, an allowlisted local origin and isolated service endpoints. Verify connection targets by non-sensitive identity/hostname and database name before any mutation; never reuse production credentials, database, queues, indices, buckets, webhook endpoints or outbound email recipients. Do not infer isolation merely from an API preview URL or a demo badge. Production writes are **not** necessary for such a test, but isolation/provisioning must be confirmed by the environment owner before executing one.

**No-migration constraint is material.** `AGENTS.md:20-22` says migration history does not provision all schema models; the API package has `prisma:push`, `prisma:migrate` and `db:seed` scripts (`apps/api/package.json`). `scripts/dev-api.cjs:125-156` may invoke `prisma:push` when the schema timestamp changes or `--force-db` is used. Do not run that bootstrap against an unknown database. A real persistence check without *any* schema change requires an already provisioned disposable database whose tables actually match the current Prisma client, including `SavedProfile`, `AIUsageLog`, `AIConversation` and `AuditLog` (`apps/api/prisma/schema.prisma`; `AGENTS.md:21`). If absent, provisioning a **separate** test database by an authorized owner is prerequisite; it cannot be called verification under a no-migration/no-schema-write rule. `PrismaService` connects on module init and fails after retries (`apps/api/src/prisma/prisma.service.ts:58-77`).

Required/conditional integrations: PostgreSQL is essential for real auth and persistence. Redis backs BullMQ email and AI jobs only when configured (`apps/api/src/mailer/email-queue.service.ts:17-56`, `apps/api/src/ai/ai-job-queue.service.ts:68-103`); disabling Redis does **not** verify queued behavior. Meilisearch falls back to Prisma when absent/unreachable (`apps/api/src/search/meilisearch.service.ts:15-33`), so search-index behavior needs its own isolated instance. SMTP, OAuth/SSO, Stripe/webhooks, S3 uploads and AI model access are separate external boundaries (`apps/api/src/mailer/mailer.service.ts`, `apps/api/src/auth/oauth.controller.ts`, `apps/api/src/sso/sso.controller.ts`, `apps/api/src/billing/billing.controller.ts:237`, `apps/api/src/uploads/uploads.service.ts:66`, `apps/api/src/ai/ollama.service.ts`); do not exercise real providers or claim those integrations pass without test-only facilities. `/api/health` probes DB/Redis/search (`apps/api/src/health/health.controller.ts:1-76`), but health alone proves neither table presence nor auth. The development stack may reuse an existing API on port 3001 (`scripts/dev-stack.cjs:104-129`); that is not proof of isolation.

The browser's preview path is particularly unsuitable as evidence: `apiRequest` routes to `resolvePreviewApiNow` on preview/demo session indicators (`apps/web/src/lib/api.ts:58-70,361-372`), while `/auth/demo` on the **real API** can create a user and issue persisted refresh tokens (`apps/api/src/auth/auth.controller.ts:177-182`, `apps/api/src/auth/auth.service.ts:208-240,264`). A real test must demonstrate network traffic to the intended isolated API, a real issued cookie/JWT and DB rows surviving reload/new session; never use preview cookies or `cfb_demo_data`. Verify CSRF cookie/header for mutations (`apps/api/src/auth/csrf.middleware.ts:10-53`) and real JWT extraction/DB validation (`apps/api/src/auth/strategies/jwt.strategy.ts:10-49`), including 401/403 and cross-account/tenant denial.

## Roles to cover (do not conflate these layers)

* **Account `Role` (six values):** `founder`, `mentor`, `investor`, `org`, `admin`, `super_admin` (`apps/api/prisma/schema.prisma:13-20`). Real registration admits only the first four (`apps/api/src/auth/auth.controller.ts:25-29`); privileged accounts need an authorized, isolated fixture/provisioning method. `RolesGuard` checks `request.user.role` against `@Roles`, not the user's persona facet (`apps/api/src/auth/guards/roles.guard.ts:10-29`). In particular, a `platform_admin` facet is not by itself an `admin`/`super_admin` account.
* **Persona `UserRoleType` (22 values):** `aspiring_founder`, `existing_founder`, `cofounder_candidate`, `technical_talent`, `business_operator`, `mentor`, `advisor`, `coach`, `course_creator`, `incubator_admin`, `accelerator_admin`, `university_admin`, `venture_studio_admin`, `angel_investor`, `vc_scout`, `vc_analyst`, `syndicate_manager`, `service_provider`, `legal_partner`, `finance_advisor`, `recruiter`, `platform_admin`. These can coexist, with primary role and `global`/`tenant`/`workspace`/`community`/`program` scopes (`apps/api/prisma/schema.prisma:23-56`, `apps/web/src/contexts/RoleContext.tsx:9-50`; role-to-dashboard mappings `apps/api/src/roles/roles.service.ts:11-144`). Each persona needs primary/secondary, missing-facet and inappropriate-scope checks where applicable; a single admin demo session cannot stand for all 22.
* **Resource membership roles:** organization `owner/admin/program_manager/mentor/reviewer/member` (`schema.prisma:74-81`); group `owner/admin/moderator/member` and tenant `owner/admin/manager/member` (`schema.prisma:293-305`); research board `viewer/editor/admin/owner` (`schema.prisma:2464-2468`); builder `owner/editor/commenter/viewer` (`schema.prisma:2848-2853`). Test membership, nonmembership, own versus another tenant/resource, and role downgrade. These are not interchangeable with global account or persona roles.

## Existing checks and explicit blockers

`AGENTS.md:3-17,21-24,29` documents jsdom frontend tests, mocked backend regression tests, static inventory and an admin-shaped demo sweep; none is a real-backend authentication/persistence suite. The previous report records 73 frontend files/662 tests and 17 backend files/240 tests, with mock limitations (`docs/UIUX_AUDIT_REVIEW.md:42-65`); those are **historical results**, not checks rerun here. `apps/api/src/ai/ai-jobs.controller.test.ts:18-101` starts a Nest HTTP server but substitutes auth, Prisma, queue and model; `apps/api/src/admin/admin.security.test.ts:5-31` mocks Prisma/transactions. Browser a11y fixtures seed a cookie/localStorage and call a mock API that explicitly has no persistence/auth/validation (`apps/web/e2e/authenticated-a11y.spec.ts:5-12,78-105`, `apps/web/e2e/mock-api.mjs:1-17`). These establish valuable UI/logic coverage, not live-service evidence.

**Blockers before claiming verification:** (1) no confirmed dedicated, current-schema disposable DB or approved test-account fixtures; (2) no verified nonproduction routing/secret segregation or safe test-only provider sinks; (3) bootstraps can schema-push and demo auth itself writes; (4) existing UI fixtures can silently substitute preview data/mock auth; (5) no full role × resource-owner × tenant × state × endpoint persistence suite, including negative cases and teardown. A read-only audit cannot resolve any of these by inspecting a running preview. Next step for the owning agent is to obtain an explicit isolated-environment guarantee and provisioned schema **without touching production**, then run narrowly scoped real HTTP auth/write/read/reload/delete checks with safe fixture cleanup and recorded destination/status evidence. Until then the result is **conditional feasibility, zero newly verified live-backend journeys**.
