# UI/UX browser review — preview proxy

## Method and coverage (2026-09-26)

Read `AGENTS.md`. Used the app's `@playwright/test` from `apps/web` against the **already running** `http://localhost:80/` preview proxy, without starting or restarting the server. Installed Playwright Chromium 141 (build 1194); the host lacks the browser's shared libraries, so a Nix shell supplied them to the browser process. The first `playwright install-deps` attempt could not use system package management in this environment. The browser subsequently launched normally; no browser validation was bypassed. Temporary browser scripts/results were used for measurement, not application code changes.

At 1440px and 390px, visited unauthenticated `/login`, `/register`, `/reset-password`, then `/dashboard`, `/discover`, `/settings`, `/settings/billing`, `/admin/dashboard`, `/messages` using **synthetic demo** `cfb_session` / `cfb_primary_role=platform_admin` cookies and demo localStorage for the latter six. This is a rendering probe for a single role, **not** proof of login or authorization. Forms were not submitted; no mutation controls were clicked. Measured navigation response, client `pageerror`, document horizontal overflow, visible-control naming heuristic, visible heading and content after a short hydration wait. The heuristic counts placeholder/title/text as a name and does not replace accessibility-tree, keyboard, contrast, or screen-reader testing.

### Observations and blockers

- The three unauthenticated auth pages rendered a form and visible bilingual desktop heading at 1440px; at 390px their headings displayed English only in the captured viewport. This is a display observation, not proof of missing Greek content or of successful form validation/submission.
- `/discover`, `/settings`, and `/settings/billing` displayed a sample/demo-data notice in desktop body text; the mobile body-text detector did not find it. Because the mobile header/chrome differs, confirm the actual notice visually before treating this as a defect. No API responses or persistence were validated.
- The admin role's `/dashboard` redirect is expected for this probe but does not cover a founder's dashboard. The admin overview and messages rendered on the later 390px retry; asynchronous loading made the initial snapshots inconclusive.
- Immediately after the full-sweep failures, fresh HTTP probes of `/login` and `/admin/dashboard` both returned **502**, and the preview screenshot attempt of `/login` failed with an HTTP response error. The already-running preview was unavailable, so no further browser checks were performed and no server was restarted. This is a preview/server availability blocker, **not** evidence that those routes intrinsically return 502 in a healthy deployment.

All API behavior, real authentication, authorization across roles, mutation effects, backend persistence, accessibility conformance, and the 138 unvisited static routes remain **NOT VERIFIED**. The observed 200s and zero counts above are narrow measurements, not a compliance certification.
